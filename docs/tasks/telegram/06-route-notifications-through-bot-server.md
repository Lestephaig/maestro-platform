# Задача 6. Направить Telegram-уведомления через зарубежный сервер бота

## Зависимости

Должны быть выполнены задачи №1–5. Эту задачу необходимо выполнить до
добавления новых типов Telegram-уведомлений в последующих этапах.

## Цель

Исключить прямое обращение Django-платформы и расположенного в России
`notification-worker` к `api.telegram.org`.

Все Telegram-уведомления должны передаваться по HTTPS в отдельный сервис
Telegram-бота на зарубежном сервере. Только зарубежный сервис должен хранить
`TELEGRAM_BOT_TOKEN` и обращаться к Telegram Bot API.

## Текущая схема

Сейчас `notification-worker`:

1. Получает ожидающую запись `NotificationDelivery` из БД.
2. Берёт `telegram_chat_id` получателя.
3. Формирует текст и inline-кнопку.
4. Самостоятельно вызывает
   `https://api.telegram.org/bot<TOKEN>/sendMessage`.

Из-за этого BotFather-токен хранится в `.env` платформы, а доставка зависит от
доступности Telegram API с российского сервера.

## Целевая схема

```text
Событие на платформе
        ↓
Django создаёт NotificationDelivery
        ↓
notification-worker в России
        ↓ HTTPS + Bearer token
зарубежный сервис Telegram-бота
        ↓ TELEGRAM_BOT_TOKEN
Telegram Bot API
```

Существующая очередь в БД, выбор каналов, статусы и повторные попытки остаются
на стороне Django-платформы. Зарубежный сервис выступает защищённым шлюзом и
не должен получать прямой доступ к БД платформы.

## Контракт API Telegram-бота

1. Добавь в сервис бота endpoint:

   ```http
   POST /internal/v1/telegram/messages
   ```

2. Endpoint должен принимать JSON следующего вида:

   ```json
   {
     "chat_id": 123456789,
     "text": "Текст уведомления",
     "parse_mode": "HTML",
     "buttons": [
       [
         {
           "text": "Открыть сообщение",
           "url": "https://www.maestrocast.ru/chat/123/"
         }
       ]
     ]
   }
   ```

3. Каждый запрос должен содержать:

   ```http
   Authorization: Bearer <TELEGRAM_DELIVERY_API_TOKEN>
   Idempotency-Key: notification-delivery-<delivery_id>
   Content-Type: application/json
   ```

4. Проверяй Bearer-токен сравнением с постоянным временем. Запрос без
   корректной авторизации должен отклоняться до отправки сообщения.
5. Валидируй:
   - `chat_id` — положительное целое число;
   - `text` — непустая строка допустимой для Telegram длины;
   - `parse_mode` — только явно разрешённые значения, для текущего сценария
     достаточно `HTML`;
   - структуру, количество и длину подписей inline-кнопок;
   - URL кнопок — только абсолютные HTTPS-ссылки;
   - максимальный размер HTTP-запроса.
6. Для отправки используй существующий сервис
   `telegram-bot/maestro_bot/service.py`, при необходимости расширив его
   поддержкой `parse_mode`.
7. Не записывай в логи BotFather-токен, delivery API token, заголовок
   `Authorization`, полный текст сообщения и полный `chat_id`.
8. Возвращай структурированный успешный ответ:

   ```json
   {
     "ok": true,
     "telegram_message_id": 1234,
     "duplicate": false
   }
   ```

9. Используй следующие категории ответов:
   - `200` — сообщение отправлено или такой запрос уже был успешно обработан;
   - `400` — некорректный payload;
   - `401` — отсутствующая или неверная авторизация;
   - `413` — превышен допустимый размер запроса;
   - `422` — Telegram окончательно отклонил получателя или сообщение;
   - `429` — временное ограничение частоты;
   - `502` или `503` — временная ошибка Telegram или сервиса.

## Идемпотентность

1. Обрабатывай заголовок `Idempotency-Key`, чтобы штатный повтор worker-а не
   создавал повторное сообщение в Telegram.
2. Повторный запрос с тем же ключом после успешной отправки должен вернуть
   `200` с `duplicate: true`, не вызывая Telegram повторно.
3. Храни успешные ключи персистентно, например в небольшой SQLite-базе на
   отдельном Docker volume.
4. Храни только хеш или значение idempotency key, статус, Telegram message ID
   и время обработки. Не сохраняй текст уведомления и `chat_id`.
5. Добавь очистку записей старше срока, превышающего максимальный период
   повторов worker-а, например старше семи дней.
6. Учти конкурентные запросы с одинаковым ключом.
7. Документируй ограничение: строгое `exactly once` невозможно гарантировать,
   если процесс завершится после принятия сообщения Telegram, но до сохранения
   результата на сервере бота.

## Изменения в Django-платформе

1. Вынеси формирование Telegram payload из `_send_telegram()` в отдельную
   тестируемую функцию.
2. Перепиши `_send_telegram()`:
   - не обращайся к `api.telegram.org`;
   - отправляй POST на `TELEGRAM_DELIVERY_API_URL`;
   - передавай `Authorization: Bearer <TELEGRAM_DELIVERY_API_TOKEN>`;
   - передавай стабильный `Idempotency-Key`, основанный на ID
     `NotificationDelivery`;
   - передавай `chat_id`, текст, `parse_mode` и кнопки по описанному контракту;
   - применяй отдельный timeout для API шлюза;
   - проверяй HTTP-статус и JSON-ответ.
3. Обрабатывай ошибки следующим образом:
   - сетевой timeout, `429` и `5xx` — вернуть доставку в `pending` и применить
     существующую экспоненциальную задержку;
   - `400`, `401`, `403`, `413` и `422` — считать постоянной ошибкой и не
     выполнять бессмысленные повторы;
   - сохранять в `last_error` только безопасный символьный код;
   - не записывать в лог URL с секретом, заголовок авторизации, текст сообщения
     и `chat_id`.
4. Сохрани проверку актуальных настроек канала непосредственно перед отправкой.
5. Не изменяй email-доставку и in-app уведомления.
6. Удали чтение `TELEGRAM_BOT_TOKEN` из `core/settings.py`.
7. Удали `TELEGRAM_BOT_TOKEN` из корневого `.env.example`, обязательных
   переменных платформы в `.github/workflows/deploy.yml` и документации
   платформы.
8. Добавь настройки:

   ```env
   TELEGRAM_DELIVERY_API_URL=
   TELEGRAM_DELIVERY_API_TOKEN=
   TELEGRAM_DELIVERY_API_TIMEOUT=10
   ```

9. В production принимай только HTTPS URL. HTTP можно разрешить для локальной
   разработки и автоматических тестов.
10. После изменений вне каталога `telegram-bot` не должно остаться прямых
    обращений к `api.telegram.org`.

## Изменения в сервисе бота

1. Добавь асинхронный HTTP-сервер в существующий процесс бота либо обоснованно
   выдели delivery API в отдельный контейнер на том же зарубежном сервере.
2. Не добавляй отдельный тяжёлый технологический стек без необходимости.
   Предпочтительный вариант для текущей архитектуры:
   - запускать лёгкий асинхронный HTTP-сервер в `post_init`;
   - корректно останавливать его в `post_shutdown`;
   - повторно использовать созданный объект Telegram Bot и его пул соединений.
3. Добавь в `BotSettings`:

   ```env
   TELEGRAM_DELIVERY_API_TOKEN=
   TELEGRAM_DELIVERY_API_HOST=0.0.0.0
   TELEGRAM_DELIVERY_API_PORT=8080
   ```

4. `TELEGRAM_BOT_TOKEN` должен остаться только в окружении зарубежного бота.
5. Добавь endpoint состояния:

   ```http
   GET /healthz
   ```

   Он не должен возвращать секреты, конфигурацию или пользовательские данные.
6. Обнови Docker Compose сервиса бота:
   - открой внутренний порт API;
   - при публикации на host привязывай его только к `127.0.0.1`;
   - добавь volume для хранилища идемпотентности;
   - расширь healthcheck проверкой HTTP API.

## HTTPS и reverse proxy

1. Опубликуй delivery API через Nginx или Caddy на зарубежном сервере, например:

   ```text
   https://bot.example.com/internal/v1/telegram/messages
   ```

2. Используй действительный TLS-сертификат.
3. Не публикуй внутренний порт контейнера напрямую в интернет.
4. Ограничь размер тела запроса и настрой разумные таймауты.
5. Если у сервера платформы постоянный публичный IP, дополнительно ограничь
   endpoint этим IP на уровне firewall или reverse proxy.
6. Bearer-аутентификация остаётся обязательной даже при IP-фильтрации.

## Переменные окружения после изменения

На платформе:

```env
TELEGRAM_BOT_NAME=MaestroBot
TELEGRAM_LINK_API_TOKEN=
TELEGRAM_DELIVERY_API_URL=https://bot.example.com/internal/v1/telegram/messages
TELEGRAM_DELIVERY_API_TOKEN=
TELEGRAM_DELIVERY_API_TIMEOUT=10
```

На зарубежном сервере бота:

```env
TELEGRAM_BOT_TOKEN=
TELEGRAM_BOT_NAME=MaestroBot
MAESTRO_BASE_URL=https://www.maestrocast.ru
MAESTRO_API_TOKEN=
TELEGRAM_DELIVERY_API_TOKEN=
TELEGRAM_DELIVERY_API_HOST=0.0.0.0
TELEGRAM_DELIVERY_API_PORT=8080
```

`TELEGRAM_LINK_API_TOKEN` платформы должен совпадать с `MAESTRO_API_TOKEN`
бота. Для delivery API с обеих сторон используется отдельный новый
`TELEGRAM_DELIVERY_API_TOKEN`. Эти два секрета нельзя объединять.

## Тесты платформы

Добавь тесты, подтверждающие:

- правильный URL и HTTP-метод;
- наличие Bearer-заголовка;
- наличие стабильного `Idempotency-Key`;
- корректную сериализацию текста и inline-кнопок;
- успешную доставку при `200` и `{"ok": true}`;
- повтор при timeout, `429` и `5xx`;
- отсутствие повтора при постоянной ошибке;
- отсутствие прямого вызова Telegram Bot API;
- отсутствие токена, текста сообщения и `chat_id` в логах;
- сохранение прежнего поведения email-доставки.

## Тесты Telegram-бота

Добавь тесты, подтверждающие:

- запуск и корректное завершение HTTP API вместе с ботом;
- `401` для отсутствующего и неверного Bearer-токена;
- `400` для некорректного JSON и полей;
- отклонение неправильного `chat_id`, URL и `parse_mode`;
- однократный вызов Telegram-сервиса для корректного запроса;
- корректную передачу HTML и inline-кнопок;
- отсутствие второй отправки для повторного `Idempotency-Key`;
- правильное преобразование ошибок Telegram в HTTP-статусы;
- отсутствие секретов и персональных данных в логах;
- корректную работу `/start`, `/help` и привязки после добавления HTTP API.

## Порядок развёртывания

1. Сгенерируй отдельный секрет доставки, например командой
   `openssl rand -hex 32`.
2. Сначала разверни delivery API на зарубежном сервере бота.
3. Настрой домен, TLS, reverse proxy и при возможности IP-фильтрацию.
4. Проверь `/healthz` с российского сервера.
5. Проверь авторизованный тестовый вызов delivery API с российского сервера.
6. Добавь URL и delivery token в `.env` платформы.
7. Разверни обновлённые платформу и worker.
8. Выполни реальную отправку через очередь `NotificationDelivery`.
9. Только после успешной проверки удали `TELEGRAM_BOT_TOKEN` из `.env`
   платформы.
10. Проверь доставку после перезапуска обоих серверов.

Такой порядок нужен, чтобы не прерывать существующую доставку во время
развёртывания.

## Документация

Обнови:

- корневой `.env.example`;
- `telegram-bot/.env.example`;
- `telegram-bot/README.md`;
- `notifications/README.md`;
- deployment-инструкции и проверку обязательных production-переменных.

Явно укажи в документации:

- BotFather-токен хранится только на зарубежном сервере;
- worker не обращается к Telegram напрямую;
- `TELEGRAM_LINK_API_TOKEN` и `TELEGRAM_DELIVERY_API_TOKEN` имеют разное
  назначение;
- недоступность зарубежного шлюза не блокирует действия пользователя на
  платформе;
- все текущие и будущие Telegram-уведомления должны использовать единый шлюз.

## Не входит в задачу

- Добавление новых типов уведомлений.
- Изменение правил подписок на объявления или музыкантов.
- Перенос email-доставки на зарубежный сервер.
- Перенос основной БД или очереди `NotificationDelivery` на сервер бота.

## Критерии приёмки

- `TELEGRAM_BOT_TOKEN` отсутствует в конфигурации сервера платформы.
- Только зарубежный сервис обращается к `api.telegram.org`.
- Worker обращается исключительно к HTTPS API зарубежного бота.
- Telegram-уведомление о новом сообщении проходит через
  `NotificationDelivery` и доходит получателю.
- Недоступность шлюза не мешает сохранить сообщение на платформе.
- Временные ошибки повторяются с экспоненциальной задержкой.
- Штатный повтор одного delivery не создаёт повторное Telegram-сообщение.
- Привязка, отвязка, `/start` и `/help` продолжают работать.
- Секреты и персональные данные не попадают в логи.
- Автоматические тесты платформы и бота проходят.
- `manage.py check`, `manage.py test` и
  `manage.py makemigrations --check --dry-run` проходят успешно.
